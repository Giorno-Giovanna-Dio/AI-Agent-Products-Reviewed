## 產品介紹

LLM Wiki 不是一套可以安裝的 App。它是 Andrej Karpathy 寫的一份想法文件，
要你貼給自己的 agent（例如 Claude Code、Codex、OpenCode 或
[Pi](https://github.com/earendil-works/pi)），再一起長出適合某個主題的
知識庫。

一般人把文件丟給模型時，多半是每次提問才重新翻原文。這份筆記提出另一
種做法：原始資料保持不動，由 agent 持續維護一份互相連結的 Markdown
wiki。人負責找來源、決定要問什麼；agent 負責摘要、改頁、對照和登記。
作者自己的用法是一邊開著 agent，一邊用 Obsidian 看頁面被改寫。

## 主要 Features

### 三層分開：原文、wiki、工作說明

原文是唯讀的來源。wiki 是 agent 產生並持續改寫的頁面，例如摘要、人物、
概念、比較和總結。第三層是一份 schema（在 Claude Code 常是 `CLAUDE.md`，
在 Codex 常是 `AGENTS.md`），寫明目錄慣例，以及收錄、回答、維護時該怎麼
做。人和 agent 會一起改這份說明，它比較像員工的職務說明，而不是又一份
筆記。

### 收錄時改很多頁，而不是只建索引

丟進一篇新來源後，agent 要讀完、寫摘要、更新目錄，並回頭修改已經存在的
相關頁面。一份來源可能動到十多頁。作者偏好一次收一篇、人在旁邊看摘要
和取捨；也可以一次收很多篇、少一點監督。流程要寫回 schema，下一個
session 才知道怎麼做。

### 好的回答要歸檔，不要留在聊天紀錄

提問時，agent 先找相關頁、再讀、再寫出有出處的答案。答案可以是一篇
Markdown、一張比較表，或其他格式。重點是：有價值的回答要存回 wiki。
比較、分析和新發現會留在知識庫裡，下一次不用從聊天紀錄重挖。

### 定期健檢

過一段時間請 agent 檢查 wiki：頁面彼此矛盾、舊說法被新來源推翻、沒有
人連到的孤頁、提到了卻沒有自己頁面的概念、缺的交叉連結，以及還可以補
的資料。這是讓知識庫變大之後還能用的維護動作。

### 目錄與日誌，先不要上搜尋引擎

`index.md` 是內容目錄：每頁一條連結、一行摘要，依類別排列。回答前先讀
目錄，再進個別頁面。作者說在大約一百份來源、數百頁的規模，這樣就夠，
不必先做 embedding 搜尋。`log.md` 是只追加的時間序，記下收錄、提問和
健檢。這兩份檔案分別回答「現在有什麼」和「最近發生什麼」。規模變大
之後，才考慮本機搜尋工具。作者提到 [qmd](https://github.com/tobi/qmd)
是一種選項，尚未在本 Cell 驗證。

## 主打賣點

- 知識要被編譯一次，然後保持最新。跨頁連結和矛盾在收錄時就處理，而不是
  每次提問才重新拼湊。
- 人會放棄 wiki，是因為維護比閱讀還累。這裡把記帳工作交給 agent：更新
  交叉引用、改過時摘要、標出矛盾。人留下策展、提問和判斷。
- 和 NotebookLM、聊天室上傳檔案、一般 RAG 不同的地方，是 wiki 本身會
  變厚。問出來的好答案也算新增的知識，不只是一次性回覆。
- 和 [gbrain](https://github.com/garrytan/gbrain) 不同：gbrain 是一套
  記憶產品，用查詢和知識圖譜把答案交還給 agent。LLM Wiki 沒有伺服器，
  產出就是你讀得完的 Markdown。Obsidian 在這裡是閱讀器，不是另一個
  記憶產品。
- Obsidian 網頁剪藏、投影片、圖表這些是可選工具。它們沒有改變「原文
  唯讀、wiki 由 agent 維護」這個分工。

## 使用情境

### 花幾週研究一個題目

- 適合誰：要連續讀論文、報導或報告，而且希望論點會隨新資料修正的人。
- 在什麼情況使用：每加一篇來源，就讓 agent 更新既有頁面，而不是另開
  一個新聊天。
- 帶來的價值：矛盾和綜合先寫在 wiki 上。下次提問是在已經整理過的頁面
  上繼續，而不是重讀全部原文。

### 讀書時做一本伴讀 wiki

- 適合誰：讀長篇作品，想留下人物、主題和情節如何互相指涉的人。
- 在什麼情況使用：每讀完一章就收錄一次，由 agent 維護交叉連結。
- 帶來的價值：讀完時手上有一本可跟著連結走的伴讀，維護成本不必自己扛。

### 團隊內部 wiki 的維護人手

- 適合誰：會議紀錄、專案文件和客戶對話一直進來，卻沒有人願意改 wiki 的
  團隊。
- 在什麼情況使用：把這些材料當來源，讓 agent 提議頁面更新，人再決定
  哪些改動可以留下。文件把人的審閱寫成一種可能，沒有規定介面。
- 帶來的價值：wiki 不會因為沒人維護而過時。哪些更新算數，仍由人收口。

## 我們可以學什麼

- 值得借鑑的 product idea：把「原始資料」、「整理後的工作成果」和「員工
  怎麼做事」分成三層。原文不能被改寫。職務說明要和人一起演進。好的
  回答是新的工作成果，不是聊天氣泡。
- 值得借鑑的 interaction / workflow：收錄、提問、健檢是三種不同任務。
  收錄時人可以站在旁邊看十多頁怎麼被改。提問結束後要有一個明確動作：
  這份答案要不要歸檔。健檢則是找出矛盾、過時說法、孤頁和缺口。
- 在 2D workspace 裡會變成什麼：一層平面圖書館。入口看板是 `index.md`。
  沿牆的時間帶是 `log.md`。原文房間上鎖，員工可以讀、不能改。wiki
  是一排可翻開的工作頁，人坐在閱讀桌看頁面被改寫。健檢時，矛盾和孤頁
  在平面上被標出來，人走過去決定留哪一說。這是員工上班的樓層，不是
  一張知識圖譜。
- 在 3D workspace 裡會變成什麼：一間走得進去的辦公室。維護 wiki 的員工
  在場。新來源送來時，你看到他在多張桌子之間走動改頁，而不是側欄跳出
  「已索引」。你坐在閱讀椅，他坐在可以動筆的位子。職務說明貼在牆上，
  你們會一起改。問出來的好答案變成新的一疊文件放上架子，而不是消失在
  對話裡。矛盾是兩張桌子之間夾著的紙條。這不是把概念做成可旋轉的立體
  圖，也不是 Conductor 那類 ADE dashboard。
- 不值得照搬或需要重新設計的地方：不要把 Obsidian 的 graph view 當成
  我們要做的 3D 辦公室。不要一開始就上 embedding 搜尋，目錄夠用時先讓
  員工讀目錄。圖片、投影片、外掛查詢都是閱讀器功能，不該變成 workspace
  的骨架。團隊情境裡「人要審過才算數」只有一句話，權限、diff 和退回都
  還沒有產品規格，必須自己設計。這份文件刻意只有模式、沒有實作。

## 初步看法

- 最有價值的部分：把知識庫的失敗原因講清楚。人不是不會想，而是不願意
  做交叉引用和改過時頁面。Agent 的工作是這份記帳，而且成果必須是人讀
  得見的頁面。
- 最大限制或疑問：它不是產品，沒有權限模型、衝突處理或多人同時改的
  規格。作者說中等規模靠目錄就夠，這是他的經驗，本 Cell 尚未驗證。
  和 gbrain 並讀時，一個是可部署的記憶層，一個是你要自己長出來的檔案
  習慣。
- 是否值得進一步研究或親自體驗：值得把它當成 workspace 的員工角色來
  研究，而不是拿去安裝。若之後要試，應看一次收錄會改哪些頁、回答有沒有
  真正歸檔，以及健檢能不能指出矛盾。在那之前 status 維持 `untried`。
